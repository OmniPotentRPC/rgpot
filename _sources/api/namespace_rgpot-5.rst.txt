Capability handshake for backends loaded through the potential profile: decide from a ``Capabilities`` message whether this build can drive the backend before any work is dispatched, and fill the same message from the producing side.

Metadata a backend leaves unset (empty family, zero bridge major) is not a declaration and is not checked. The constants mirror the eindir-core objective ABI stamp that rgpot-core compares against.

Backends (nwchemc, cpmdc, future lammpsc/gromacsc) export the same C symbol set prefix-parameterized on ``<p>`` (see potentials-schema PROFILE.md). This loader resolves that whole set from one dlopen'd shared library, so rgpot drives every conforming backend through identical function pointers with no per-backend loader code. Everything stays native: flat binary Cap'n Proto messages both directions, plain C calls in-process.

A :ref:`BatchEvaluator <doxid-classrgpot_1_1_batch_evaluator>` owns one potential instance per worker, created by a caller-supplied factory, and splits the configurations of one call into contiguous ranges, one range per worker. Instances share nothing, so no potential has to be re-entrant across threads; a potential that reports ``PotCaps::reentrancy`` as process-serial is safe here because each instance is touched by one thread at a time.

.. ref-code-block:: cpp

	:ref:`rgpot::BatchEvaluator <doxid-classrgpot_1_1_batch_evaluator>` eval(
	    [] { return std::make_unique<rgpot::LJPot>(); }, 4);

A worker that throws stops its range; evaluate() rethrows the exception of the lowest-numbered failing worker after every worker has joined.

One independent calculator is one group. A NEB image or a dimer end is that group, and ranks in a group share a subcommunicator. bindCalculators is collective on MPI_COMM_WORLD. Every rank calls it before the first force. shareFromCalculator broadcasts from the first rank of calculator owner onto MPI_COMM_WORLD. forceImpl fills :ref:`ForceOut <doxid-structrgpot_1_1_force_out>` on the rank that calls it.

librgpot never links MPI. The MPI side lives in librgpot_mpi (meson dependency and pkg-config name rgpot-mpi), which bindCalculators and calculatorsUseMpi load with dlopen on first use through the C ABI in :ref:`calculator_mpi_abi.h <doxid-calculator__mpi__abi_8h_source>`. A process that never calls them never maps libmpi; until the library is loaded every call below behaves as in a build without MPI.

The three file layouts of the LAMMPS pair_eam page (docs.lammps.org/pair_eam.html):

Funcfl pair_style eam one element: F(rho), Z(r), rho(r) Setfl pair_style eam/alloy F_a(rho), rho_a(r), r phi_ab(r) FinnisSinclair pair_style eam/fs F_a(rho), rho_ab(r), r phi_ab(r)

E = sum_i F_a(rho_i) + sum\_{i<j} phi_ab(r_ij), with a the element of atom i, b that of j, and rho_i = sum\_{j != i} rho_ab(r_ij), the density a b neighbor puts at an a site. Setfl has rho_ab = rho_b. The FinnisSinclair layout is the Finnis and Sinclair form, Phil. Mag. A 50, 45 (1984).

The tables go through the LAMMPS steps, so energies and forces follow pair_style eam to rounding: funcfl arrays resampled onto lround((N-1) d / d) points by four-point Lagrange, r phi = 27.2 \* 0.529 \* Z(r)^2, the seven-coefficient cubic of PairEAM::interpolate, and F extended linearly in the energy above rhomax. Pairs count when r < cutoff.

Each atom is matched to an element by its atomic number against the first field of the element line. LAMMPS ignores that field and maps by name instead. Only one funcfl file is read, so funcfl is one element.

A potential whose energy is a sum of site terms, E = sum_i E_i, where each E_i depends only on the atoms within a distance ``cutoff`` of atom i, has a non-virtual member

:ref:`Locality <doxid-structrgpot_1_1_locality>` locality() const noexcept;

The ``:ref:`LocalPotential <doxid-conceptrgpot_1_1_local_potential>``` concept detects it, the way ``:ref:`PerAtomPotential <doxid-conceptrgpot_1_1_per_atom_potential>``` detects forcePerAtom, so a caller holding the concrete type can split the work over regions of space without a new virtual on ``:ref:`PotentialBase <doxid-classrgpot_1_1_potential_base>``` or a new field in ``:ref:`PotCaps <doxid-structrgpot_1_1_pot_caps>```.

Then the force on atom k, -sum_i dE_i/dr_k, depends only on the atoms within 2 \* cutoff of k: the sites i within cutoff of k and their own neighbours. When every term of E is a function of one pair distance (``pairwise``), it depends only on the atoms within cutoff. That radius is ``forceRange``. A host can therefore evaluate the potential on its own atoms plus every atom within ``forceRange`` of them, free of periodic images, and keep the forces, the site energies and the per-atom virials (:ref:`PerAtom.hpp <doxid-_per_atom_8hpp_source>`) of its own atoms: they equal those of the whole system.

A potential with the staged evaluation of :ref:`Staged.hpp <doxid-_staged_8hpp_source>` needs less: atoms within ``cutoff`` and an exchange of ``densities`` values per atom between its two stages, which carries what the neighbours of the neighbours contribute.

A cutoff of 0 declares no finite range (a whole-system or long-range potential, or a truncation switched off).

With :math:`t = (r - r_\mathrm{on}) / (r_c - r_\mathrm{on})` clamped to :math:`[0, 1]`,

.. math::

	S(t) = 1 - 10 t^3 + 15 t^4 - 6 t^5,\qquad
	S'(t) = -30 t^2 (1 - t)^2 .

The coefficients are the unique quintic with :math:`S(0) = 1`, :math:`S'(0) = S''(0) = 0` and :math:`S(1) = S'(1) = S''(1) = 0`, so :math:`V(r) S(t(r))` and its first two derivatives are continuous at :math:`r_\mathrm{on}` and vanish at :math:`r_c` for any smooth :math:`V`. scripts/validation/pair_kernels.py derives them and checks the C^2 conditions symbolically; scripts/validation/quintic_switch.sollya bounds the binary64 evaluation error of the Horner forms used here.

The clamp is a min/max pair, so evaluation carries no branch: below :math:`r_\mathrm{on}` it returns :math:`S = 1`, :math:`dS/dr = 0` exactly.

An embedded-atom potential walks its pairs twice: the first pass sums each atom's density, and the second needs the embedding of both ends of a pair before it can write that pair's force. The powers and quotients of the distance that the force takes are mostly ones the first pass already had. ``:ref:`PairTerms <doxid-classrgpot_1_1_pair_terms>``` keeps a few doubles for each pair the first pass accepts, and the second pass reads them back.

Two walks over one neighbour update visit the same pairs in the same order with the same separations, so when both passes accept a pair by the same test, the k-th pair the second pass accepts is the k-th one the first pass kept. A team walk has the same order within each thread, and takes one ``:ref:`PairTerms <doxid-classrgpot_1_1_pair_terms>``` per thread.

Potentials fingerprint their configuration into ``:ref:`PotentialBase::paramsKey() <doxid-classrgpot_1_1_potential_base_1af6ed01a80dc945fcc1f8a0735aa36621>``` so cached results never cross parameter sets. Hash field by field — never memcpy a struct (padding bytes).

A host that splits space over processes, such as LAMMPS, holds its own atoms and copies of the atoms around them (periodic images, and atoms that another process owns), and builds the neighbour list itself. A potential with a finite range (:ref:`Locality.hpp <doxid-_locality_8hpp_source>`) that has the two members

void densityStage(const HalfList &, double \*densities) const; void forceStage(const HalfList &, const double \*densities,
                  double \*forces, StageTally \*tally) const;

evaluates its host's atoms on that list with copies out to its cutoff, not out to :ref:`Locality::forceRange <doxid-structrgpot_1_1_locality_1a50fd1bccd98f35b81d45d59bb9813554>`. The density stage adds the pair terms of each atom's densities (the electron density of :ref:`EAM <doxid-class_e_a_m>` and Sutton-Chen) into an array the host has zeroed, :ref:`Locality::densities <doxid-structrgpot_1_1_locality_1a1ce3c32b2d6406d29a3f76260f8f7be0>` consecutive values per atom. The host then completes them: with HalfList::newton it first adds the values written to copies into their owners, and in every case it copies each owner's values to its copies. The force stage takes the embedding of every atom from its densities and the pair forces from the densities at both ends of each pair. This is the pair_style eam scheme with one difference: the host communicates rho where pair_style eam communicates F'(rho), and the force stage takes F' of the copies too, so no third stage runs between the exchanges. A pairwise potential has no densities; its density stage does nothing and the host skips the exchange.

The ``:ref:`StagedPotential <doxid-conceptrgpot_1_1_staged_potential>``` concept detects the two members, as ``:ref:`PerAtomPotential <doxid-conceptrgpot_1_1_per_atom_potential>``` detects forcePerAtom, so they add no virtual function to ``:ref:`PotentialBase <doxid-classrgpot_1_1_potential_base>```. The helpers in ``rgpot::staged`` hold the loop over the list and the share of each pair that a host keeps.
