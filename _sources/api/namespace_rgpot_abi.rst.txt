.. ref-code-block:: cpp
	:class: doxyrest-title-code-block

	std::uint32_t kCxxLayoutRevision = 1

Hand-maintained. Increment when a change the hash cannot see alters the C++ ABI: reordering virtuals without changing their count, changing the meaning of a field, changing a base class of a covered type. Any change to size, alignment or a field offset moves the hash by itself.

.. index:: pair: variable; kCxxSoversion
.. _doxid-_cxx_layout_8hpp_1a0c75c1c32154159824631e3ca3f6f3c4:

.. ref-code-block:: cpp
	:class: doxyrest-title-code-block

	std::uint32_t kCxxSoversion = 4

ELF soversion of librgpot (``librgpot.so.N``, ``librgpot.N.dylib``). Meson and CMake read this constant. The SONAME is not the layout hash. The hash depends on the platform tag and includes the cache feature bit, so builds of one revision do not share a hash. Bump this when a recorded hash in ``kCxxSoversionTable`` changes, and replace that table from the CI stamp lines in the same edit. ``check_cxx_soversion.py`` fails when the fingerprint of the stamp inputs changes and this number did not increase.

This is not ``RGPOT_ABI_LAYOUT_REVISION``. The C ABI stamp in ``rgpot.h`` stayed at major 1, minor 0, layout revision 1: no exported C struct changed layout. The C API is exported from librgpot, so it has no shared library of its own and rides this SONAME. ``librgpot_mpi`` stays at soversion 3 (``RGPOT_MPI_ABI_VERSION`` 1, unchanged).

	std::string check_server(::Potential::Client& server, kj::WaitScope& wait_scope, const :ref:`Expectation<doxid-structrgpot_1_1abi_1_1_expectation>`& want = {})

Ask a connected server for its ``Capabilities`` and return empty when it is compatible, else the reason. A server built before ``Potential.getCapabilities`` existed answers UNIMPLEMENTED; that is reported as a missing call with the upgrade path, never as a successful handshake.
