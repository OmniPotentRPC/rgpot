* Quantum and machine-learned potentials

The potentials on this page do not evaluate a formula that rgpot owns.
Each one hands the atoms to a tight-binding library, a quantum-chemistry engine
or a machine-learned model, and converts the answer to the rgpot units:
positions in Angstrom, energy in eV and forces in eV/Angstrom.
The "functional form" part of each section therefore says which method runs,
what rgpot does around it (unit conversion, wavefunction reuse, neighbour
lists), and where the method's own parameters live.

The per-class entries are in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]].
The C ABIs of the engines that are opened with =dlopen= are in
[[file:../reference/quantum_abi.org][Quantum engine C ABIs]] and
[[file:../reference/engine_abi.org][Engine C ABI]].
The names that =rgpot-eval=,
=pair_style rgpot= and the PLUMED action accept are in [[file:../reference/potential_names.org][Potential
names and options]].
None of the potentials below has such a name, so none is reachable from those
three tools.

None of xtb, tblite, libtorch, NWChem, CPMD, CP2K, MOPAC or ORCA is installed on
the machine that builds this page.
Most examples therefore compile against the rgpot headers but do not run, and
each section says what to install to run them.
The blocks that do run print the error a missing engine gives.
Every program that needs a build feature carries a =requires= marker, so a build
without that feature skips it.

Energies are converted with the constants in =CppCore/rgpot/units.hpp=:

| Constant                | Value             | Meaning                   |
|-------------------------+-------------------+---------------------------|
| =BOHR_TO_ANGSTROM=      | 0.529177210903    | Angstrom per bohr         |
| =HARTREE_TO_EV=         | 27.211386245988   | eV per Hartree            |
| =KB_HARTREE=            | 3.1668115634556e-6 | Hartree per kelvin       |

A force is minus the gradient, so a gradient in Hartree/bohr is multiplied by
=NEG_GRAD_TO_FORCE=, which is minus =HARTREE_TO_EV= over =BOHR_TO_ANGSTROM=.

|---------------+---------------+----------------------------+-----------------------|
| =XTB=         | =XTBPot=      | libxtb                     | =-Dwith_xtb=true=     |
| =TBLite=      | =TBLitePot=   | libtblite                  | =-Dwith_tblite=true=  |
| =Metatomic=   | =MetatomicPot= | libtorch, metatomic model | =-Dwith_metatomic=true= |
| =Uma=         | =UmaPot=      | libtorch, UMA =.pt2=       | =-Dwith_uma=true= or =-Dwith_metatomic=true= |
| =NWChem=      | =NWChemPot=   | =libnwchemc=               | =-Dwith_rpc=true=     |
| =Skala=       | =SkalaPot=    | =libnwchemc= with Skala    | =-Dwith_skala=true=   |
| =CPMD=        | =CPMDPot=     | =libcpmdc=                 | =-Dwith_rpc=true=     |
| =CP2K=        | =CP2KPot=     | =libcp2kc_rgpot=, libcp2k  | =-Dwith_cp2k=enabled= |

| =ORCA=        | =ORCAPot=     | the =orca= executable      | =-Dwith_orca=true=    |

The defaults in =meson_options.txt= are false for =with_xtb=,
=with_tblite=, =with_metatomic=, =with_uma=, =with_skala=,
=with_orca= and =with_rpc=, and =disabled= for =with_cp2k=.

enables both.
=with_skala= and =with_cp2k= also need =with_rpc=.
=MOPACPot= is always built and opens =libmopacc= at run time.

** =XTB= GFN tight binding through libxtb

*** What it is

=XTBPot= (=CppCore/rgpot/XTBPot/XTBPot.hpp=) runs GFN0-xTB, GFN1-xTB, GFN2-xTB
or GFN-FF from the xtb library, which it links at build time.
Use it for molecules and clusters when a quantum surface is needed at a cost of
milliseconds per atom set.
=XTBDlopen= (=CppCore/rgpot/XTBPot/XTBDlopen.hpp=) runs the same method through
=libxtb_engine.so=, so a host does not link libxtb.
=XTBDlopen= is always built, and the engine library is built by the same
=-Dwith_xtb=true= build.
There is no Python class, no =rgpot-eval= or =pair_coeff= name, and the
=potserv= type names are =XTB= (GFN2-xTB), =GFNFF=, =GFN1xTB= and =GFN0xTB=.
=potserv= knows them only in a build with xtb.
The class entries are under "xtb" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]], and the
engine ABI is in [[file:../reference/engine_abi.org][Engine C ABI]].

*** Functional form

xtb returns the total energy of the chosen method at the geometry, and its
gradient.
The method papers below define that energy, and the parameter files are part of
xtb. rgpot adds no term and applies no cutoff, shift or species rule of its own.
Every element the method is parametrized for is accepted, by atomic number.
These are the steps the source takes in =CppCore/rgpot/XTBPot/XTBPot.cc=:

- Positions and the cell are multiplied by =ANGSTROM_TO_BOHR=.
  The molecule is built with all three periodicity flags false, so the cell does
  not enter the energy.
- Energy in eV is the Hartree energy times =HARTREE_TO_EV=.
- Forces are the gradient times =NEG_GRAD_TO_FORCE=.
- When the cell volume is positive, the stress is the xtb virial in Hartree
  times =HARTREE_TO_EV= divided by the volume, in eV/Angstrom^3.
  Otherwise =has_stress= is 0.
- The first force builds the molecule and loads the parametrization.
  A later force with the same atomic numbers only updates the geometry.
  A change of composition builds the molecule again.
- The previous self-consistent wavefunction is the next guess while no atom
  moved by more than
  =warm_move= and the HOMO-LUMO gap is at least =warm_min_gap=.
  Otherwise the results object is replaced, so the energy does not depend on the
  call history.
- The first pass is capped at the smaller of =max_iterations= and 48 iterations.
  After an unconverged pass the source tries 1000 K, 3000 K and 5000 K in turn,
  skipping a rung that is not above =electronic_temperature=.
  Each rung starts from fresh results and is followed by a pass at the
  configured temperature, and the first rung that converges ends the ladder.
  When none converges the call throws =rgpot::SccNotConverged=.
  The energy returned is that of the configured temperature.

*** Parameters

Every row is a field of =XTBConfig= in =CppCore/rgpot/XTBPot/XTBConfig.hpp=.

| Parameter                | Value     | Unit     | Set in                          |
|--------------------------+-----------+----------+---------------------------------|
| =method=                 | =GFN2xTB= | none     | =XTBConfig::method=             |
| =accuracy=               | 1.0       | none     | =XTBConfig::accuracy=           |
| =electronic_temperature= | 300.0     | K        | =XTBConfig::electronic_temperature= |
| =max_iterations=         | 250       | none     | =XTBConfig::max_iterations=     |
| =charge=                 | 0.0       | e        | =XTBConfig::charge=             |
| =uhf=                    | 0         | unpaired electrons | =XTBConfig::uhf=      |
| =warm_move=              | 1.0       | Angstrom | =XTBConfig::warm_move=          |
| =warm_min_gap=           | 1.0       | eV       | =XTBConfig::warm_min_gap=       |

=method= takes =GFNFF=, =GFN0xTB=, =GFN1xTB= or =GFN2xTB=.
=XTBDlopenConfig= adds =engine_path=, empty by default.
The 48-iteration cap and the 1000, 3000 and 5000 K ladder are constants in
=XTBPot::forceImpl= and =XTBPot::rescueUnconvergedScc=.
The GFN parameters have no copy in rgpot.

*** Example

Build with libxtb 6.6 or newer (=xtb= in =pixi.toml= is pinned to =>=6.6.0,<7=)
and turn the option on:

#+attr_rgpot: syntax
#+begin_src bash
pixi shell -e xtbbld
meson setup bbdir -Dwith_xtb=true
meson compile -C bbdir
#+end_src

The program below evaluates water with GFN2-xTB in a 100 Angstrom cell.
It needs libxtb, so it compiles here only in a build with =with_xtb= on.

#+attr_rgpot: compile link=rgpot requires=has_xtb
#+begin_src cpp
#include <cstdio>

#include "rgpot/XTBPot/XTBPot.hpp"

int main() {
  rgpot::XTBConfig cfg;
  cfg.method = rgpot::GFNMethod::GFN2xTB;
  rgpot::XTBPot pot(cfg);

  const double pos[9] = {0.0, 0.0,      0.11779,  //
                         0.0, 0.75545,  -0.47116, //
                         0.0, -0.75545, -0.47116};
  const int z[3] = {8, 1, 1};
  const double box[9] = {100.0, 0.0, 0.0, 0.0, 100.0, 0.0, 0.0, 0.0, 100.0};
  double forces[9] = {};
  rgpot::ForceInput in{3, pos, z, box};
  rgpot::ForceOut out{};
  out.F = forces;
  pot.forceImpl(in, &out);
  std::printf("energy %.6f eV, has_stress %d\n", out.energy, out.has_stress);
  std::printf("force on O, z: %.6f eV/Angstrom\n", forces[2]);
  return 0;
}
#+end_src

The geometry is the one =TBLitePotTest= uses.
No energy is printed here, because this machine has no libxtb.
This repository does not pin a GFN2 energy for it either.

** =TBLite= GFN tight binding through libtblite

*** What it is

=TBLitePot= (=CppCore/rgpot/TBLitePot/TBLitePot.hpp=) runs GFN1-xTB, GFN2-xTB or
IPEA1-xTB from the tblite library, which it links at build time.
Use it where xtb is not available or where a tblite-based stack is already in
place.
The potential has no dlopen frontend, no Python class and no =rgpot-eval= or
=pair_coeff= name.
The =potserv= type names are =TBLite= and =TBLiteGFN2= (GFN2-xTB), =TBLiteGFN1=
and =TBLiteIPEA1=, in a build with tblite.
The class entry is under "tblite" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]].

*** Functional form

tblite returns the total energy of the method and its gradient.
The method papers define the energy, and tblite holds the parameters.
There is no cutoff, shift or species rule in rgpot.
The source in =CppCore/rgpot/TBLitePot/TBLitePot.cc= does this:

- Positions and the cell go to tblite in bohr.
  The periodicity argument is null, so the structure is not periodic.
- The temperature goes to tblite in Hartree, as
  =electronic_temperature= times =KB_HARTREE=.
- Energy in eV is the Hartree energy times =HARTREE_TO_EV=.
  Forces are the gradient times =NEG_GRAD_TO_FORCE=.
- With a positive cell volume, the stress is the tblite virial in Hartree times
  =HARTREE_TO_EV= divided by the volume, in eV/Angstrom^3.
  Otherwise =has_stress= is 0.
- The first force builds the structure and the calculator from that call's
  atoms, including =charge= and =uhf=.
  Later forces only update the geometry, and do not check the composition, so
  use one =TBLitePot= for each composition.
- A failed SCF replaces the result object, so the next call does not start from
  the failed wavefunction.

*** Parameters

Every row is a field of =TBLiteConfig=, declared in
=CppCore/rgpot/TBLitePot/TBLitePot.hpp=.

| Parameter                | Value  | Unit               | Set in                               |
|--------------------------+--------+--------------------+--------------------------------------|
| =method=                 | =GFN2= | none               | =TBLiteConfig::method=               |
| =accuracy=               | 1.0    | none               | =TBLiteConfig::accuracy=             |
| =electronic_temperature= | 300.0  | K                  | =TBLiteConfig::electronic_temperature= |
| =max_iterations=         | 250    | none               | =TBLiteConfig::max_iterations=       |
| =charge=                 | 0.0    | e                  | =TBLiteConfig::charge=               |
| =uhf=                    | 0      | unpaired electrons | =TBLiteConfig::uhf=                  |

=method= takes =GFN1=, =GFN2= or =IPEA1=.
The method parameters are the ones shipped with tblite, and rgpot holds no copy.

** =Metatomic= machine-learned models through metatomic

*** What it is

=MetatomicPot= (=CppCore/rgpot/MetatomicPot/MetatomicPot.hpp=) loads a metatomic
TorchScript model and evaluates it in process with libtorch.
Use it for any model exported in the metatomic format, for example a
machine-learned interatomic potential.
=MetatomicDlopen= (=CppCore/rgpot/MetatomicPot/MetatomicDlopen.hpp=) reaches the
same model through =libmetatomic_engine.so=, so a host does not link libtorch.
In Python, =rgpot.evaluate_metatomic= and =rgpot.evaluate_metatomic_dlopen= are
functions on that engine; there is no Python potential class.
The =potserv= type name is =Metatomic:<model_path>[:<device>]=, in a build with
metatomic.
There is no =rgpot-eval= or =pair_coeff= name.
The class entries are under "Metatomic" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]], the Python
functions are in [[file:../reference/python_api.org][the Python API]], and the
engine route is in [[file:engine-metatomic.org][Metatomic and the engine ABI]].

*** Functional form

The model defines the surface, and rgpot only differentiates it.
The source in =CppCore/rgpot/MetatomicPot/MetatomicPot.cc= does this:

- Positions are in Angstrom, converted to the model dtype, with gradients
  required.
  The cell is passed as given, and an axis whose cell vector has length of at
  most 1e-9 is not periodic.
- The neighbour lists the model requests are built with vesin.
- The model's =energy= output is summed over atoms, or over the batch entry for
  a per-system output.
- Forces are minus the autograd gradient of that energy with respect to the
  positions.
  No stress is written.
- With =n_symmetry_rotations= above 0, the model runs on that many rotated
  copies of the geometry, rotated about the centroid, and the energy and forces
  are averaged over them.
  With =random_rotation= alone there is one rotated copy and no average.
- The variance is the mean-square residual of the force.
  It sums the squared difference between each copy's force and the returned
  force over every copy, atom and Cartesian component, and divides by the number
  of those terms.
  Its unit is (eV/Angstrom)^2, and it is not the RMS spread, so take one square
  root to get a force scale.
  It is 0 when there is a single pass.
  With =so3_probe_scatter= the unrotated copy gives the energy and forces, and
  the residuals of the rotated copies are measured from that force.
- With =uncertainty_threshold= above 0 and a per-atom =energy_uncertainty=
  output in the model, the variance is instead =energy_uncertainty_mean=
  squared.
  Here =energy_uncertainty_mean= is the mean of that output over the atoms of
  the first pass, in eV.
  Its unit is eV^2, and one square root recovers the mean.
  The threshold only switches the output on; its value is never compared with
  anything.
  A model without a per-atom =energy_uncertainty= output turns the switch off
  and the force residual above is reported.
- Two or more systems evaluated together without rotation in one model call
  report a variance of 0.
- =charge= and =spin= are attached as system data named =rgpot::charge=,
  =rgpot::spin_multiplicity= and =rgpot::spin= when the model lists them in =requested_inputs=.
  =attach_system_extras= attaches all three whatever the model lists.

No cutoff, shift or species rule is applied by rgpot.
The cutoffs and the species are those of the model.

** =Uma= UMA models through AOTInductor packages

*** What it is

=UmaPot=
(=CppCore/rgpot/UmaPot/UmaPot.hpp=) evaluates a UMA (Universal Model for Atoms) checkpoint that =scripts/export_uma_aoti.py=
has exported to an AOTInductor package (=.pt2=).
Use it when a UMA surface is needed for a molecule or a periodic cell, for
example along a NEB band, since the class evaluates a band in one call. rgpot
builds the neighbour list with its own pair search and passes it to the compiled
graph, which does not call fairchem.
There is no Python class, no =rgpot-eval= or =pair_coeff= name, and no dlopen
frontend in =librgpot=.
The =potserv= type names are =Uma:<model_path>= and =Uma:<model_path>:<task>=,
where =<task>= is one of =omol=, =omat=, =oc20=, =oc22=, =oc25=, =odac= and
=omc=, in a build with metatomic.
The class entry is under "UMA" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]], and the
export is in [[file:uma-export.org][Export a UMA model with dynamic shapes]].

*** Functional form

The package defines the surface.
It returns the energy and the forces, and rgpot copies both unchanged: the
package must return eV and eV/Angstrom, which the exporter's packages do.
No stress is written.
What rgpot does in =CppCore/rgpot/UmaPot/UmaPot.cc= is the graph input:

- The neighbour list is a full pair list with periodic images along all three
  cell vectors and a strict cutoff.
  Zero-distance pairs are dropped.
  Each atom keeps its =max_neighbors= nearest neighbours.
  Edges are sorted by center, distance, neighbour and cell shift, so a run is
  reproducible.
- The cutoff is =cutoff= unless the package carries its own, which wins.
  A cutoff that is not positive and finite becomes 6.0 Angstrom.
- Charge and spin go to the graph as per-call integer tensors.
  The spin is the multiplicity.
- A package is exported for one task, charge and spin, and for a composition or
  a range of compositions.
  A force call compares the config and the input with the package metadata and
  throws =rgpot::UmaContractError= or =rgpot::UmaShapeError= on a mismatch.

*** Parameters

Every row is a field of =UmaConfig= in =CppCore/rgpot/UmaPot/UmaConfig.hpp=.

| Parameter        | Value  | Unit     | Set in                      |
|------------------+--------+----------+-----------------------------|
| =model_path=     | empty  | path     | =UmaConfig::model_path=     |
| =task_name=      | =omol= | none     | =UmaConfig::task_name=      |
| =device=         | =cpu=  | none     | =UmaConfig::device=         |
| =charge=         | 0      | e        | =UmaConfig::charge=         |
| =spin=           | 1      | multiplicity | =UmaConfig::spin=       |
| =cutoff=         | 6.0    | Angstrom | =UmaConfig::cutoff=         |
| =max_neighbors=  | 300    | none     | =UmaConfig::max_neighbors=  |
| =cache_dir=      | empty  | path     | =UmaConfig::cache_dir=      |

The weights are in the checkpoint, and the package records which checkpoint it
came from (=UmaPot::checkpointProvenance=). rgpot holds no copy of them.
An empty =cache_dir= means =$RGPOT_CACHE_DIR=, then =$XDG_CACHE_HOME/rgpot=,
then =.rgpot-cache= in the working directory.

** =NWChem= quantum chemistry through libnwchemc

*** What it is

=NWChemPot= (=CppCore/rgpot/NWChemPot/NWChemPot.hpp=) evaluates Hartree-Fock or
density functional theory with NWChem.
Use it for molecules at a first-principles level.
The class opens =libnwchemc=, the split engine of the nwchemc project, with
=dlopen=. rgpot builds no NWChem engine of its own.
The options travel as the =NWChemParams= message.
There is no Python class and no =rgpot-eval= or =pair_coeff= name.
The =potserv= type name is =NWChem[:basis[:theory[:xc]]]=.
The class entries are under "NWChem" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]], and the
ABI is in [[file:../reference/quantum_abi.org][Quantum engine C ABIs]].

*** Functional form

The surface is the NWChem total energy for the theory, basis and charge in
=NWChemParams=.
=theory= =scf= with =scfType= =rhf= or =uhf= is Hartree-Fock, and =theory= =dft=
takes the exchange-correlation functional from =scfType= or from a typed =dft=
stanza. rgpot applies no cutoff, shift or species rule.
The source in =CppCore/rgpot/NWChemPot/NWChemPot.cc= does this:

- Positions go to the engine in Angstrom, and the energy comes back in Hartree.
  The gradient comes back in Hartree/bohr.
- Energy in eV is the Hartree energy times =HARTREE_TO_EV=.
  Forces are the gradient times =NEG_GRAD_TO_FORCE=.
- The cell is not sent, and the class reports =periodic = false=.
  No stress is written.
- =potserv= turns =NWChem:<basis>:<theory>:<xc>= into those fields.
  When =<xc>= is given it adds one raw input block: a =dft= block with =xc <xc>=
  and =iterations 60=, with each comma of =<xc>= replaced by a space.

*** Parameters

The rows are the fields of =NWChemParams= in
=CppCore/rgpot/rpc/Potentials.capnp=, with the schema defaults.
=NWChemPot= sends them unchanged unless the caller sets them.

| Parameter      | Value        | Unit | Set in                         |
|----------------+--------------+------+--------------------------------|
| =basis=        | =sto-3g=     | none | =NWChemParams.basis=           |
| =theory=       | =scf=        | none | =NWChemParams.theory=          |
| =scfType=      | =rhf=        | none | =NWChemParams.scfType=         |
| =charge=       | 0            | e    | =NWChemParams.charge=          |
| =multiplicity= | 1            | 2S+1 | =NWChemParams.multiplicity=    |
| =enginePath=   | empty        | path | =NWChemParams.enginePath=      |
| =nwchemRoot=   | empty        | path | =NWChemParams.nwchemRoot=      |
| =task=         | =gradient=   | none | =NWChemParams.task=            |
| =title=        | empty        | none | =NWChemParams.title=           |
| =memoryMb=     | 0            | MB   | =NWChemParams.memoryMb=        |
| =scratchDir=   | empty        | path | =NWChemParams.scratchDir=      |
| =permanentDir= | empty        | path | =NWChemParams.permanentDir=    |
| =inputBlocks=  | empty list   | text | =NWChemParams.inputBlocks=     |
| =inputStanzas= | empty list   | none | =NWChemParams.inputStanzas=    |

Basis sets and functionals are NWChem's own libraries. rgpot holds no copy of

** =Skala= the Skala functional on NWChem

*** What it is

=SkalaPot= (=CppCore/rgpot/SkalaPot/SkalaPot.hpp=) is Kohn-Sham DFT in NWChem
with the Skala exchange-correlation functional, a neural-network functional.
Use it when a deep-learned XC functional is wanted on molecules.
It is not a separate surface: =SkalaPot= builds an =NWChemParams= message with
=theory= =dft= and the Skala keyword, and evaluates it through =NWChemPot= and
=libnwchemc=.
The =potserv= type names are =Skala= and =Skala:<basis>=, in a build with
=with_skala=.
There is no Python class and no =rgpot-eval= or =pair_coeff= name.
The class entries are under "Skala" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]].

*** Functional form

The energy is the NWChem Kohn-Sham energy with Skala as the exchange-correlation
term.
The functional itself is defined in the paper below, and the engine evaluates
it. rgpot only writes the keyword.
The source in =CppCore/rgpot/SkalaPot/SkalaPot.cc= does this:

- It sets =theory= to =dft=, =task= to =gradient=, and the basis, charge and
  multiplicity from the config.
- It adds one typed =dft= stanza whose =xc= is the config's =xc= keyword.
- Units, signs and the missing cell and stress are those of =NWChemPot=.
- The constructor throws =std::runtime_error= when =basis= or =xc= is empty or
  =multiplicity= is below 1.
  A =setParams= failure of the inner =NWChemPot= is ignored.
- The generic engine route for Skala reads only the basis, charge, multiplicity,
  engine path and NWChem root, and keeps the default =xc=.

The engine has to be an NWChem build that accepts the =skala-1.1= keyword. rgpot
does not check that.

Every row is a field of =SkalaConfig= in
=CppCore/rgpot/SkalaPot/SkalaConfig.hpp=.

| =basis=        | =def2-tzvp=  | none | =SkalaConfig::basis=        |
| =charge=       | 0            | e    | =SkalaConfig::charge=       |
| =multiplicity= | 1            | 2S+1 | =SkalaConfig::multiplicity= |
| =engine_path=  | empty        | path | =SkalaConfig::engine_path=  |
| =nwchem_root=  | empty        | path | =SkalaConfig::nwchem_root=  |

** =CPMD= plane-wave density functional theory through libcpmdc

*** What it is

=CPMDPot= (=CppCore/rgpot/CPMDPot/CPMDPot.hpp=) evaluates plane-wave DFT with
CPMD.
Use it for periodic or isolated systems where plane waves and norm-conserving
pseudopotentials are wanted.
The class opens =libcpmdc=, the split engine of the cpmdc project, with
=dlopen=, and sends the =CPMDParams= message.
It does not write CPMD decks itself.
There is no Python class and no =rgpot-eval= or =pair_coeff= name.
The =potserv= type name is =CPMD=.
The class entries are under "CPMD" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]], and the
ABI is in [[file:../reference/quantum_abi.org][Quantum engine C ABIs]].
The walk-through with a stand-in engine is in
[[file:../tutorials/cpmd.org][Evaluate a water geometry with CPMD]].

*** Functional form

The energy is the CPMD Kohn-Sham total energy for the functional, plane-wave
cutoff and pseudopotentials in =CPMDParams=.
The default functional is BLYP, which is Becke exchange with Lee-Yang-Parr
correlation. rgpot applies no cutoff, shift or species rule of its own.
In =CppCore/rgpot/CPMDPot/CPMDPot.cc=:

- Positions go to the engine in Angstrom and the energy comes back in Hartree,
  so the energy in eV is that times =HARTREE_TO_EV=.
  The gradient in Hartree/bohr is converted with =NEG_GRAD_TO_FORCE=.
- The box of the call is the cell CPMD uses when it is not all zero.
  An all-zero box keeps the cell of the deck.
  The README in =CppCore/rgpot/CPMDPot/README.md= gives the details.
- The stress is copied when the engine reports one, and then =has_stress= is 1.
  An engine tensor in Hartree/bohr^3 is multiplied by
  =HARTREE_PER_BOHR3_TO_EV_PER_ANGSTROM3=.
- Every rank of a calculator group enters a force call together.
  A failure is printed on every rank, and then =MPI_Abort= runs on the world.
- The typed =atoms= section carries the pseudopotentials by element symbol.
  Without it the engine's built-in BLYP defaults cover hydrogen and oxygen only.

*** Parameters

The rows are the fields of =CPMDParams= in =CppCore/rgpot/rpc/Potentials.capnp=,
with the schema defaults.

| Parameter       | Value      | Unit | Set in                       |
|-----------------+------------+------+------------------------------|
| =functional=    | =BLYP=     | none | =CPMDParams.functional=      |
| =cutOffRy=      | 70.0       | Ry   | =CPMDParams.cutOffRy=        |
| =charge=        | 0          | e    | =CPMDParams.charge=          |
| =multiplicity=  | 1          | 2S+1 | =CPMDParams.multiplicity=    |
| =task=          | =gradient= | none | =CPMDParams.task=            |
| =title=         | empty      | none | =CPMDParams.title=           |
| =memoryMb=      | 0          | MB   | =CPMDParams.memoryMb=        |
| =scratchDir=    | empty      | path | =CPMDParams.scratchDir=      |
| =permanentDir=  | empty      | path | =CPMDParams.permanentDir=    |
| =cpmdRoot=      | empty      | path | =CPMDParams.cpmdRoot=        |
| =enginePath=    | empty      | path | =CPMDParams.enginePath=      |
| =inputBlocks=   | empty list | text | =CPMDParams.inputBlocks=     |
| =inputSections= | empty list | none | =CPMDParams.inputSections=   |

Pseudopotential files and their parameters are CPMD's own, and rgpot holds no

*** What it is

=CP2KPot= (=CppCore/rgpot/CP2KPot/CP2KPot.hpp=) evaluates Gaussian and plane
wave (GPW) DFT with CP2K Quickstep.
Use it for periodic cells and larger systems than the Gaussian-basis engines
reach.
It renders a CP2K input deck from =CP2KParams= and the first geometry, then
loads =libcp2kc_rgpot=, a thin shim over libcp2k, with =dlopen=.
There is no Python class and no =rgpot-eval= or =pair_coeff= name.
The =potserv= type name is =CP2K=, in a build with =with_cp2k=.
The class entries are under "CP2K" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]].
The walk-through is in
[[file:../tutorials/cp2k.org][Evaluate diamond silicon with CP2K]].

*** Functional form

The energy is the Quickstep total energy of the deck.
With an empty =inputTemplate=, =CppCore/rgpot/CP2KPot/CP2KDeck.cc= writes a GPW
deck from the typed fields:

- =&MGRID= with =CUTOFF= and =REL_CUTOFF=.
- =CHARGE=, =MULTIPLICITY=, and =UKS= when =uks= is set.
- =&SCF= with =SCF_GUESS ATOMIC=, =EPS_SCF=,
  =MAX_SCF= and =IGNORE_CONVERGENCE_FAILURE=, an =&OT= block with the DIIS minimizer and the =FULL_SINGLE_INVERSE= preconditioner when =ot= is set, and an =&OUTER_SCF=
  block when =outerMaxScf= is above 0.
- =&XC_FUNCTIONAL= named by =functional=.
- One =&KIND= for each element, with =basisSet= and =pseudopotential=.
- A =&CELL= with the =PERIODIC= setting from =periodic=.

A non-empty =inputTemplate= is used as written, apart from the
=@RGPOT_COORD@= and =@RGPOT_CELL@= tokens, which =setParams= requires. rgpot
applies no cutoff or species rule outside the deck.
In =CppCore/rgpot/CP2KPot/CP2KPot.cc=:

- Positions and the cell go to the shim in bohr.
  The energy in eV is the Hartree energy times =HARTREE_TO_EV=.
- libcp2k returns forces and not gradients, so the force is the shim's value in
  Hartree/bohr times =HARTREE_TO_EV= over =BOHR_TO_ANGSTROM= with no sign
  change.
- No stress is written.
- An unconverged SCF throws =rgpot::CP2KScfError= on every rank without
  aborting; another failure ends in =MPI_Abort=.
- The session is created at the first force, and again only when the atomic
  numbers or the parameters change.

*** Example

Build the shim against a libcp2k that ships =libcp2k.pc=, such as the
conda-forge =cp2k= package.
The option is a feature, and it needs RPC:

#+attr_rgpot: syntax
#+begin_src bash
pixi shell -e mpibld
meson setup bbdir -Dwith_rpc=true -Dwith_mpi=enabled -Dwith_cp2k=enabled
meson compile -C bbdir
#+end_src

The program evaluates water in a 12 Angstrom cube with PBE.
It compiles here only in a build with =with_cp2k= on.

#+attr_rgpot: compile link=rgpot requires=has_cp2k
#+begin_src cpp
#include <cstdio>

#include <capnp/message.h>

#include "rgpot/CP2KPot/CP2KPot.hpp"

int main() {
  capnp::MallocMessageBuilder msg;
  auto params = msg.initRoot<CP2KParams>();
  params.setFunctional("PBE");
  params.setCutoffRy(650.0);
  params.setRelCutoffRy(70.0);
  rgpot::CP2KPot pot(params.asReader());

  const double pos[9] = {0.0, 0.0,      0.11779,  //
                         0.0, 0.75545,  -0.47116, //
                         0.0, -0.75545, -0.47116};
  const int z[3] = {8, 1, 1};
  const double box[9] = {12.0, 0.0, 0.0, 0.0, 12.0, 0.0, 0.0, 0.0, 12.0};
  double forces[9] = {};
  rgpot::ForceInput in{3, pos, z, box};
  rgpot::ForceOut out{};
  out.F = forces;
  pot.forceImpl(in, &out);
  std::printf("energy %.6f eV\n", out.energy);
  return 0;
}
#+end_src

There is no output here, because this machine has no libcp2k.

** =MOPAC= semiempirical models through libmopacc

*** What it is

=MOPACPot= (=CppCore/rgpot/MOPACPot/MOPACPot.hpp=) evaluates a semiempirical
NDDO model with OpenMOPAC.
Use it for fast, rough quantum energies of molecules.
The class opens =libmopacc=, the split engine of the mopacc project, with
=dlopen=, and always builds.
There is no Python class, no =rgpot-eval= or =pair_coeff= name, and no =potserv=
type name.
The class entries are under "MOPAC" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]], and the
ABI is in [[file:../reference/quantum_abi.org][Quantum engine C ABIs]].

*** Functional form

The energy is the one OpenMOPAC reports for the model, converted by rgpot.
=model= picks the Hamiltonian, by the number of the =MOPACC_MODEL_*= constants
in =CppCore/rgpot/MOPACPot/mopac_c_abi.h=: 0 is PM7, 1 PM6-D3H4, 2 PM6-ORG, 3
PM6, 4 AM1 and 5 RM1. rgpot applies no cutoff, shift or species rule, and the
model parameters are those of libmopac.
In =CppCore/rgpot/MOPACPot/MOPACPot.cc=:

- Positions go to the engine in Angstrom unchanged.
  The energy comes back in Hartree and the gradient in Hartree/bohr.
- Energy in eV is the Hartree energy times =HARTREE_TO_EV=.
  Forces are the gradient times =NEG_GRAD_TO_FORCE=.
- The cell is not sent, the class reports =periodic = false=, and no stress is
  written.
- A force throws =std::runtime_error= when the engine is not loaded, =nAtoms= is
  not positive, a buffer is null, or the engine reports failure.
  The failure text always begins with "mopacc AM1 failed", whatever =model= is.

*** Parameters

Every row is a field of =MOPACPot::Config= in
=CppCore/rgpot/MOPACPot/MOPACPot.hpp=.

| Parameter     | Value | Unit                | Set in                  |
|---------------+-------+---------------------+-------------------------|
| =charge=      | 0     | e                   | =MOPACPot::Config::charge= |
| =spin=        | 0     | not stated in source | =MOPACPot::Config::spin=  |
| =model=       | 4     | model number (AM1)  | =MOPACPot::Config::model= |
| =tolerance=   | 1.0   | not stated in source | =MOPACPot::Config::tolerance= |
| =max_time=    | 3600  | not stated in source | =MOPACPot::Config::max_time= |
| =engine_path= | empty | path                | =MOPACPot::Config::engine_path= |

The header gives no unit for =spin=, =tolerance= or =max_time=, and they reach
=libmopacc= in the packed =MopacCParams= struct, which is also where their
meaning is defined.
The model parameters are not in rgpot.

*** Example

OpenMOPAC has to be built as =libmopacc= from the mopacc project, which this
repository does not do.
There is no meson option for it. rgpot finds the library by =enginePath=,
=MOPACC_LIBRARY=, =RGPOT_MOPACC_ENGINE= or the name =libmopacc.so= on the loader
path.

The program below runs here.
It selects PM6, and shows what a host sees when no engine is installed:

#+attr_rgpot: run link=rgpot
#+begin_src cpp
#include <cstdio>
#include <exception>

#include "rgpot/MOPACPot/MOPACPot.hpp"

int main() {
  rgpot::MOPACPot::Config cfg;
  cfg.model = 3;
  rgpot::MOPACPot pot(cfg);
  std::printf("available: %d\n", pot.available() ? 1 : 0);

  const double pos[9] = {0.0, 0.0,      0.11779,  //
                         0.0, 0.75545,  -0.47116, //
                         0.0, -0.75545, -0.47116};
  const int z[3] = {8, 1, 1};
  const double box[9] = {};
  double forces[9] = {};
  rgpot::ForceInput in{3, pos, z, box};
  rgpot::ForceOut out{};
  out.F = forces;
  try {
    pot.forceImpl(in, &out);
  } catch (const std::exception &e) {
    std::printf("force failed: %s\n", e.what());
  }
  return 0;
}
#+end_src

#+attr_rgpot: output printed by the block above
#+begin_example
available: 0
force failed: MOPAC engine (libmopacc) not loaded: libmopacc not loaded: dlopen failed: mopacc.dll: mopacc.dll: cannot open shared object file: No such file or directory
#+end_example

With =libmopacc= installed, the same program prints no failure line and =forces=
holds the PM6 forces; this machine cannot show that.

** =ORCA= quantum chemistry through the orca executable

*** What it is

=ORCAPot= (=CppCore/rgpot/ORCAPot/ORCAPot.hpp=) runs one ORCA energy and
gradient per force call.
Use it for molecular single points with any method ORCA offers, from DFT to
coupled cluster.
The class starts the =orca= executable as a child process and reads back the
=.engrad= file, so rgpot links no ORCA library and carries no ORCA code.
It is built with =-Dwith_orca=true=, which needs =fork= and =exec= and so is not
available on Windows.
There is no Python class, no =rgpot-eval= or =pair_coeff= name, and no =potserv=
type name.
The class entries are under "ORCA" in
[[file:../reference/cpp_backends.org][C++ engine-backed potentials]], and the
walk-through is [[file:orca.org][ORCA single points]].

*** Functional form

The energy is the one ORCA reports for the method, basis and keywords of the
config, converted by rgpot.
In =CppCore/rgpot/ORCAPot/ORCAFiles.cc= and =CppCore/rgpot/ORCAPot/ORCAPot.cc=:

- The input carries =method=, =basis= and =keywords= on the =!= line followed by
  =EnGrad=, =%maxcore=, =%pal nprocs= when =nprocs= is above 1, and the atoms in
  a =* xyz= block with =charge= and =multiplicity=.
- Positions go to ORCA in Angstrom unchanged, the unit of a =* xyz= block.
  The =.engrad= energy comes back in Hartree and the gradient in Hartree/bohr.
- Energy in eV is the Hartree energy times =HARTREE_TO_EV=.
  Forces are the gradient times =NEG_GRAD_TO_FORCE=.
- With =restart= on, the orbitals of a successful call start the next one with
  the same atomic numbers, through =%moinp= and =MORead=.
- The class reports =periodic = false=, a force with a non-zero box entry throws
  =std::invalid_argument=, and no stress is written.
- A failed run throws =rgpot::ORCAError=, whose message ends with the tail of
  ORCA's standard error and output file.

*** Parameters

Every row is a field of =ORCAConfig= in =CppCore/rgpot/ORCAPot/ORCAPot.hpp=.

| Parameter      | Value | Unit         | Set in                       |
|----------------+-------+--------------+------------------------------|
| =executable=   | empty | path         | =ORCAConfig::executable=     |
| =method=       | empty | none         | =ORCAConfig::method=         |
| =basis=        | empty | none         | =ORCAConfig::basis=          |
| =keywords=     | empty | none         | =ORCAConfig::keywords=       |
| =charge=       | 0     | e            | =ORCAConfig::charge=         |
| =multiplicity= | 1     | 2S+1         | =ORCAConfig::multiplicity=   |
| =nprocs=       | 1     | processes    | =ORCAConfig::nprocs=         |
| =maxcore_mb=   | 1024  | MB / process | =ORCAConfig::maxcore_mb=     |
| =restart=      | true  | none         | =ORCAConfig::restart=        |
| =scratch_dir=  | empty | path         | =ORCAConfig::scratch_dir=    |
| =keep_files=   | false | none         | =ORCAConfig::keep_files=     |
| =timeout_s=    | 3600  | s            | =ORCAConfig::timeout_s=      |

=method= is required, and the constructor throws =std::invalid_argument= when it
is empty.
An empty =executable= looks up =orca= on =PATH=, and an empty =basis= suits a
composite method that carries its own.
A =timeout_s= of 0 waits with no limit.
The method and basis parameters are ORCA's own, and rgpot holds no copy.

*** Example

ORCA is installed separately under its own license; this repository does not
build or fetch it.
The option only compiles the class:

#+attr_rgpot: syntax
#+begin_src bash
meson setup bbdir -Dwith_orca=true
meson compile -C bbdir
#+end_src

The program evaluates water with PBE in the def2-SVP basis.
It compiles here only in a build with =with_orca= on.

#+attr_rgpot: compile link=rgpot requires=has_orca
#+begin_src cpp
#include <cstdio>

#include "rgpot/ORCAPot/ORCAPot.hpp"

int main() {
  rgpot::ORCAConfig cfg;
  cfg.method = "PBE";
  cfg.basis = "def2-SVP";
  cfg.keywords = "TightSCF";
  rgpot::ORCAPot pot(cfg);

  const double pos[9] = {0.0, 0.0,      0.11779,  //
                         0.0, 0.75545,  -0.47116, //
                         0.0, -0.75545, -0.47116};
  const int z[3] = {8, 1, 1};
  double forces[9] = {};
  rgpot::ForceInput in{3, pos, z, nullptr};
  rgpot::ForceOut out{};
  out.F = forces;
  pot.forceImpl(in, &out);
  std::printf("energy %.6f eV\n", out.energy);
  return 0;
}
#+end_src
